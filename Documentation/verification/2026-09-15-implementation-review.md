## 表示上限変更とキャッシュ

### 再現

1. 64px 上限の読み込みをソース内で停止する。
2. 上限を 128px へ上げ、新しい読み込みだけを完了させる。
3. 上限を 64px に戻す。この操作は既存の大画像を保持する仕様。
4. 古い 64px の読み込みを完了させる。

変更前は「現在の上限が読み込み開始時と同じ」という判定だけで旧画像を格納し、
128px のキャッシュを 64px で上書きした。回帰テストの画像同一性と高さの検査が
ともに失敗した。

### 変更

- Book が単独所有する PageCache を MainActor 上の同期操作へ整理。
  キャッシュ照会・読み込み登録・無効化の間に別タスクが割り込まない。
  画像デコードは引き続き独立タスクで実行する。
- 完了時は読み込みの登録世代を照合し、失効した結果を格納しない。
- 上限を下げただけなら進行中の大画像も活かし、再デコードを避ける。
- 上限の直接書き換えをやめ、無効化処理を通る更新メソッドへ統一。

`BookConcurrencyTests` の 2 件で完了順を制御して検査する。
既存の LRU・メモリ上限・見開き寸法索引のテストも通過。

### 命中コストの A/B

`Scripts/bench/page-cache.swift` を実際の変更前後の PageCache とそれぞれリンク。
両方を Swift 6 モード、macOS 26 ターゲット、`-O` でコンパイルした。
128 件を 20,000 回参照し、変更前/後を交互に 3 巡。
各プロセスの先頭ラウンドを除いた計 15 回の値を比較した。

| 20,000 回の命中 | 中央値 | 最小–最大 |
|---|---:|---:|
| 変更前 (actor 間の移動あり) | 156.086 ms | 154.268–158.233 ms |
| 変更後 (Book と同じ MainActor) | 0.862 ms | 0.793–2.954 ms |

全ラウンドのチェックサムは 160,000 で一致。
これは索引の命中コストで、アプリ全体のページ表示の倍率ではない。
実画像 32 枚、合計 256 MiB の一括解放も別プローブで確認し、変更前は
1.18–1.55 ms、変更後は 0.95–1.74 ms だった。より大きなキャッシュや
他の負荷がある状態まで、この値で一般化はしない。

## 非同期のページ移動・見開き取得

### 再現

ヘッダ取得や画像取得を継続で停止し、後発の操作を先に実行した。
変更前に次の 4 件が失敗した。

| 待機中の処理と後発操作 | 変更前の結果 |
|---|---|
| 位置 4 から戻る途中で先頭へジャンプ | 現在位置が `-1` |
| 巻末へ移動する途中で位置 1 へジャンプ | 古い巻末判定が位置 3 で上書き |
| 見開き区分を再調整する途中で位置 1 へジャンプ | 位置 0 へ戻される |
| ページ 0 の画像取得中にページ 2 を表示 | ページ 0 の画像に位置 2 の番号が付く |

### 変更と回帰検査

- 見開き取得は、位置・ソート・見開き条件の変更を世代で検出して再計算する。
  画像・番号・次の送り幅を同じ状態から確定する。
- 後退/巻末判定は開始位置を固定し、各待機後にナビゲーションの世代を照合する。
  後発のジャンプや設定変更で失効した結果は反映せず、巻頭/巻末の操作へも流さない。
- 同方向の後退どうしが重なった場合は、新しい位置から再判定して両操作を反映する。
- 後退と巻末移動の重複した見開き判定を共通化した。
- Controller 側も、待機後に対象の Book が現在の本かを照合する。

`BookNavigationConcurrencyTests` は上記 4 件に加え、連続した後退、古い見開き取得と
新しい単ページの送り幅、取得中の読みモード変更、取得中のソート変更を検査する。
全 8 件が通過した。既存の Book・見開き判定・ページ寸法索引も回帰なし。

## ページカールの準備・取消・連続操作

### 再現

Controller の入力共通入口と本の差し替えを名前付きメソッドへ抽出し、動作を
変える前に実際の Controller / ReaderView / Book と停止可能な BookSource で検査した。
通常のウインドウ初期化・本を開くフローは使わず、実ユーザーの設定や履歴は書き換えない。

| 条件 | 変更前の結果 |
|---|---|
| 画像取得待ちのカールを取り消す | 位置が仮移動先に残り、同期で元へ戻らない |
| 有効なカールを取り消し、そのまま位置 4 へジャンプ | 旧取消 Task が後から逆移動し、位置 3 へ戻される |
| 本 A の画像取得待ちに本 B のカールを開始し、A を先に完了 | B の `starting` が旧処理で終了状態に上書きされる |

初期 3 テストは 4 assertion の失敗。修正後に同じ経路で通過した。

### 変更と検査

- 操作のセッションが対象本・復元点・着地点・準備 Task を持つ。
  非同期処理の完了は同じ操作が所有する場合だけカール状態へ反映する。
- 取消は着地点の位置とナビゲーション世代を照合し、元の位置・表示枚数・先読み方向を
  同期復元する。同じ番号への再ジャンプも別操作として保護する。
- 確定済みの連続スワイプは前の見開き枚数まで待つ。
  `0-1 → 単ページ2 → 3-4` の送り幅と、ヘッダ待機中の `4 → 2 → 0` を確認した。
  後の操作だけを取り消しても、前の確定した移動とその表示を維持する。
- OS の `.cancelled` は移動距離にかかわらず取消。本の切替・終了で待機と入力追跡を終了する。
  次の操作が成立しなかった場合も、リセットした元ページを再表示する。
- `refreshDisplay` はリサンプルキャッシュ照会後にも表示世代・本・位置を照合する。
  カールのスナップショット予約と一回消費フラグはこのガードの後に渡す。
- 巻き戻し Timer の遅延通知はオーバーレイの同一性と巻き戻し世代で照合し、
  新しい Timer/オーバーレイに触れない。ビューを外したときも Timer を終了する。

回帰は `InteractiveCurlConcurrencyTests` の 13 件。既存のルール 3 件、
`PageCurlRenderTests` の実描画 5 件も通過。実トラックパッドからのイベント配送は
今回の自動テストでは検査していない。キャッシュ照会直後のガードと Timer の
世代照合はコード上の所有権検査であり、その瞬間だけを止める再現実験とは区別する。

## ページ番号・保存マークの境界

実際の `PageLayout.swift` を Swift 6 / `-O` で単体プローブにリンクした。
Go to Page は UI ソースから変換式を取り出して同じプローブへ入れた
(ダイアログ操作そのものの試験ではない)。変更前後に同じ引数を与えた。

| 入力 | 変更前 | 変更後 |
|---|---|---|
| 保存マーク `Int.min` の文字列 | SIGTRAP | 派生集合では無視 |
| マーク `-1-2` | ページ 1・2 を強制ペアにする | 無視 |
| マーク `2-5` | ページ 2・5 を強制ペアにする | 無視 |
| マーク `01` | ページ 1 を単ページ化 | 旧標準表記と異なるため無視 |
| マーク `4-5` | ページ 4・5 を強制ペアにする | 同じ |
| Go to Page の `Int.min` | 減算で SIGTRAP | 先頭へクランプ |
| 内部 API `setForcedSingle(Int.max)` | 加算で SIGTRAP | 不正な index を無視 |

不正マークも保存用の raw 配列には保持し、解釈だけを限定する。
境界の有効値 `Int.max` のページ番号と末尾隣接ペアは、作成・削除とも正常。
`Book.skip` は足し算の前に移動量を本の範囲へ制限する。

追加は PageLayout 4 件と Book 2 件。保存の既存テストを含む 74 件、続いて
全体 673 件が通過した。Go to Page の変換式と PageMarks のプローブも全 7 条件で正常終了。

**到達可能性の区別:** マークの解析とページ番号入力は外部の保存値/テキストを直接受ける。
一方、マーク編集 API の `Int.max` や skip の `Int.max` は内部 API の境界検査。
通常のスキップ設定は `Double.safeInt` が ±9e18 に制限するため、疑っていた
`backSkip` の `Int.min` 符号反転は到達できず、修正対象から除外した。

- 正常 ZIP 1 冊と破損 ZIP/PDF 2 冊を含むフォルダで、組み立て進捗が

## 複数の固定レイアウト EPUB の描画

画像1枚へ還元できないテキスト入り FXL をメモリ内で組み、画面外の実 WebKit で
描画した。RGB の背景色を変え、戻った画像がそれぞれの出版物に対応することも確認した。

変更前は 3 出版物の並行描画で、3冊目のレンダラ生成が先の2冊を `invalidate()` し、
2件が `CancellationError` で失敗した。同じ publication を共有する未使用ソースを
別に作って破棄すると、使用中ソースの後続5件も取り消された。2テストで計7失敗。

変更後はレンダラを使用中にする期間に2枠のゲートを使い、アイドルの LRU だけを
入れ替える。保持上限は2個。同じ publication の要求は同じ枠へ合流し、
Washi 内の FIFO を維持する。破棄通知はソース固有の所有者 ID を外し、
他のソースや描画が使っているレンダラには触れない。ソース自身も描画完了まで保持し、
解放通知が所有者登録より前へ抜けないようにする。

上記2回帰と取消要求後の別冊描画が通過。関連 EPUB テスト19件、全体678件も通過した。
Washi のソースは `invalidate`/FIFO 契約の確認に読み取りだけで使用し、変更していない。
保持数の制約はゲートと利用数の構造、および Debug の assertion で検査している。
WebContent プロセスの RSS や実書籍コーパス全体の性能を測った主張ではない。

## 本の移動と状態ファイルの書き込み失敗

テスト専用フォルダで本を移動し、URL bookmark が移動先を追う状態を作った。
移行先の空の状態ファイルだけに immutable 属性を付け、実ファイルへの atomic 書き込みを
失敗させた。変更前は旧状態ファイルの 1,989 バイトが削除され、ストアを作り直すと
しおりと最終ページを失った。1 テストで 3 assertion が失敗した。

移行先への保存が成功したときだけ、旧状態ファイルを削除するようにした。
失敗時には旧ファイルを保持し、失敗した新パスのメモリキャッシュを外すことで
次の参照でも移行を再試行する。最近使った本は実際の移動先へ追従させ、
「履歴内の本だけ最終ページを復元する」設定でも現在の読書位置を読み戻せる。

同じテストで旧ファイルのバイト列保存、書き込み可能に戻した後の再試行、
別ストアからのしおりと最終ページの復元まで通過した。関連する状態保存・
EPUB 位置保存・ファイル判定の 55 テストも通過。属性変更と defaults はテスト専用で、
実ユーザーの本や履歴は使っていない。

## ルーペの非同期取得

実 ReaderView をテスト専用の画面外ウインドウへ載せ、ソースのルーペ画像取得を
停止して完了順を制御した。通常表示と区別できる寸法の画像を使い、実際のレイヤーに
貼られた画像を検査した。変更前は、別の本の同じページ ID への差し込みと、
同じ本の旧要求による新要求の上書きがそれぞれ失敗した(2 テスト・2 assertion)。

要求 Task を保持し、次の要求・表示失効で取消す。本・位置・要求世代・表示世代を
各 await 後に照合し、設定値と PageEntry を要求中に固定する。
前段でノイズ低減したルーペ画像のリサイズキーにも、その低減段階を含めた。
2 回帰と共通表示処理を使うカール 13 件が通過した。

暗号化フラグを await 後の別の本から読む箇所も要求時の値へ揃えた。
ただし現在のルーペの拡大は MetalFX で、この呼び出しでは ML のディスクキャッシュへ
保存しないため、フラグの不一致を平文保存の再現としては扱わない。

## ML 代替画像の再利用と回復

ML が使えない状態の `.strong` ノイズ低減は CI の代替結果を保持する。
同じ元画像を別サイズへリサイズすると中間結果へ命中するが、変更前はこの命中を
本物の ML 結果とみなし、モデル回復後も派生した別サイズの代替画像が残った。
既存の中間再利用テストへ回復後のキャッシュ照会を追加し、1 assertion の失敗を再現した。

中間結果に付けた代替フラグを最終結果へ引き継ぐように修正。
ノイズ低減を1回にまとめる再利用は維持し、回復時には別サイズの派生画像も破棄する。
補間・ノイズ低減の26テストが通過した。XCTest の既存 ML 無効化経路を使い、
モデルのダウンロードや実モデルの推論品質比較は行っていない。

## 補助ページ操作の対象

見開き切替の画像取得待ちに本を外すと、旧本のマークだけが後から変更されることを
再現した。保存対象がない状態で再開するため、実ユーザーの履歴は使わない。
操作開始時の本と位置を待機後に照合し、旧本への変更を止めた。

同じ照合をゴミ箱操作と読み取り対象の決定にも適用。ゴミ箱は確認ダイアログ後にも
対象を再照合する。原寸画像のタイトルとファイル情報の各 Entry は、I/O 待機前に
固定する。ファイル情報の再要求は世代で照合し、古い取得が新パネルを上書きしない。
競合回帰1件、Book の非同期移動8件、ファイル情報8件の計17件が通過した。
Finder の起動や実ファイルのゴミ箱移動は実行していない。

## オープン処理の終了と後発要求

テスト用暗号化ソースを既存の事前準備スロットへ入れ、解除判定の2回目を停止した。
XCTest の既存モーダル抑止により、実パスワードや保管庫を使わず取消経路を通す。
変更前は「解除中に閉窓」「解除中に別のオープン要求」「Task 開始前に閉窓」の
3条件で計4 assertion が失敗し、古い本のプレースホルダを後から表示した。

オープン世代を要求時に同期採番し、閉窓は画像本/EPUB の提示世代を失効させる。
解除結果は成功・取消とも表示前に照合し、進捗ハンドラを設定する await 後も
旧本の後始末へ進む前に確認する。パスワード UI の提示も世代で照合する。
3回帰と EPUB 解析/カールの23件が通過し、最後のガード追加も関連46件で検証した。

## EPUB の進行率境界

EPUB ジャンプの実ソースから整数変換に至る式を取り出し、Swift 6 / `-O` の
隔離プローブで実行した。NaN は変更前に SIGTRAP、変更後は正常終了で無視する。
無限大も入口で拒否する。0・0.5・1 の有効値は同じ結果だった。
バインディングの旧保存形式は NSNumber の非有限値も読み込めるが、通常の割合選択 UI が
NaN を生成するという主張ではない。実 Controller + EPUBReaderView でも
非有限値3種を渡す回帰テストが通過した。

## framework の更新判定と同梱物

Washi / KaitoKit の両ラッパーについて、コンパイラ・署名を小さな fixture に
置き換えて実スクリプトの更新判定と配置を実行した。変更なしではビルド1回のまま。
ソース削除・更新日時を戻した内容変更・古い日時のファイル追加は、変更前は
全6条件で再ビルドせず、変更後は全6条件で2回目のビルドを実行した。

更新日時の比較をファイル名と内容の SHA-256 に替え、Swift の版・ソース位置・
アーキテクチャの既存判定と組み合わせた。KaitoKit の兄弟ビルダにも時刻による省略が
あるため、内容変更時は兄弟の生成 framework を外して再生成させる。
兄弟のソースと SwiftPM キャッシュは変えない。Washi のスタンプは署名成功後に確定する。

Xcode 側にも、既存出力だけでスクリプト全体を省略する設定があった。
増分 Debug ビルドのログでは3フェーズとも実行されていなかったため、
毎回スクリプトを呼び、内部の軽い更新判定へ委ねる設定に揃えた。
最終の Debug test / Release 増分 build では、3フェーズの実行と
各スクリプトの `up to date`、ビルド/テスト成功をログで確認した。

実 checkout の Sources/Package.swift に対するハッシュ計算は3回の測定で
KaitoKit 27.1–30.5 ms、Washi 19.4–33.9 ms。コンパイラ照会・ビルド時間は含まず、
キャッシュが効いたファイルシステム上での測定である。

Credits と同梱物には Washi の表記と MIT 本文がなかったため、兄弟 checkout の
LICENSE を `Washi-LICENSE.txt` として加え、Credits から参照した。
既存の KaitoKit / Sparkle / ML モデルの表記は維持する。
Release 内のライセンスと Credits は入力のバイト列に一致した。
KaitoKit / Washi は生成元と埋め込み先の Mach-O UUID が一致し、古い埋め込みはない。
アプリは arm64、同梱 framework は KaitoKit / Washi / Sparkle の3個だった。

## 検証基盤と範囲

XCTest の4クラスの setup/teardown は MainActor へ明示的に渡し、隔離違反の
警告を解消した。設定テストの一意な defaults スイートも終了時に消す。
アトラステストの可変時計は MainActor のオブジェクトへ移し、Sendable クロージャの

framework 参照を含む型検査が失敗したため維持した(冗長という警告だけで消さない)。

レビューは Book/キャッシュの整合性を中心に、書庫/PDF/EPUB のソースと寿命、
リーダーの移動・表示・ルーペ・補助操作、永続化と保護コンテンツの保存、
リサンプル/ML/GPU の受け渡し、バインディングの数値境界、ビルドと同梱物を横断した。
上記の再現実験・回帰と、全686テスト、シェル/Python構文、差分の空白検査で確認した。
全ての実書籍や入力機器の組合せを網羅した証明ではない。
実トラックパッドのイベント配送、NAS 実機、実 ML モデルの品質/速度比較、
Finder/Trash 操作、公開・公証は今回の検査に含めていない。
