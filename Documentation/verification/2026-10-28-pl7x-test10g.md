# 高遅延入力の 7z 並列復号の受入れ計測(Test_10G、2026-10-28)

cooViewer-pl7x(高遅延判定で 7z の並列復号を切ると、キャッシュ済み書庫で中間ジャンプ 2.2 倍・定常 0.4 倍に退行)と、
cooViewer-31v8 から移した残り(reset の多い大きな `-mmt=8` 7z での Test_10G の退行確認)の計測記録。
KaitoKit の K2-1 / K3-1 / K4-1(98008f3・50f41c7 相当、v0.16.0)の効果を、修正前の版と比べる。
計測は orchestrator が行った。道具と生の結果は `2026-10-28-pl7x/` に置く。

## 1. 結論

- **pl7x は解消している。** キャッシュ済み(warm)の書庫で、B の定常は A より 6% 速い(2,639 / 2,490 MB/s、2,722 / 2,566 MB/s)。
  open から中間ジャンプまでの累計は A と同じ(67 / 68 ms、31 / 35 ms)。並列が戻らない書庫(mid-mt1)では A と B は同じになる。
  並列復号が切れたままなら、big-tiff の定常は mid-mt1 と同じ 41 MB/s 程度まで落ちるはずだが、そうなっていない。
- **31v8 の残りも解消している。** cold の 1 枚目は big-jpeg で 8,493 → 20 ms、big-tiff で 351 → 14 ms。31v8 の当時は 24〜51 s だった。
- **事前に決めた基準のうち、warm の「1 段ごとの jump」は満たしていない**(big-jpeg 29 → 65 ms、big-tiff 16 → 28 ms)。
  A は reset の走査を 1 枚目で払い、B はそれを 2 回目の要求(この計測では jump)へ回すので、この基準は並列の有無ではなく
  走査の時期を測っていた。そのため、合否は cold と同じく**累計**で判定するよう基準を改めた。改めたことをここに明記する。

## 2. 条件

| 項目 | 値 |
|---|---|
| A | KaitoKit v0.15.0(高遅延判定なし。並列復号は常に有効) |
| B | KaitoKit v0.17.0(出荷版。`inputLatency` は既定の `.automatic`、SMB なので high と判定) |
| ハーネス | `2026-10-28-pl7x/main.swift`。両版の worktree に path 依存させ、それぞれ release で build。既定の `ReaderOptions` で URL から開く |
| クライアント | M4 Max(この記録の作業機)。Spotlight・WindowServer など通常のデスクトップ負荷あり。Codex・ビルドは止めた |
| サーバー | Mac mini M4 の `~/Test_10G`(SMB、10GbE) |
| 1 試行 | 1 process で open → 先頭の entry → 50% 位置の entry(jump)→ その後ろから末尾まで(steady)を順に読む |
| 正しさ | 読んだ全 bytes の SHA-256 を書庫ごとに比べ、全 72 試行で一致した |

### 書庫(mini の上で生成。クライアントは生成時に一度も読んでいない)

画像は `Scripts/bench/makecorpus.swift`(決定論的)で作った。TIFF はその PNG を `sips` で無圧縮 TIFF に変換した。

| 書庫 | 中身 | 作り方 | 大きさ | LZMA2 の reset 点 |
|---|---|---|---:|---:|
| big-jpeg.7z | JPEG 200 枚(403 MB) | `7zz a -t7z -m0=lzma2:c=8m -mx5 -mmt=8 -ms=on` | 403 MB | 49 |
| big-tiff.7z | TIFF 100 枚(384 MB) | 同上 | 15.6 MB | 46 |
| mid-mt1.7z | JPEG 100 枚(201 MB) | `7zz a -t7z -m0=lzma2 -mx5 -mmt=1 -ms=on` | 201 MB | 1(対照) |

reset 点は `Scripts/bench/lzma2walk.c` で数えた。既定の block の大きさでは big-jpeg / big-tiff とも 3〜4 点しかなかったので、
`c=8m` で作り直した。**big-jpeg は 8,252 chunk のうち 7,572 が無圧縮 chunk で、復号の大半が複写になる。**
並列復号の効果を表すのは、326 chunk がすべて LZMA の big-tiff のほうである。

### 状態

- cold: 試行の直前に mini の上で `cp -c`(clonefile)した複製を作り、試行の後すぐ消した。新しい inode なので
  クライアントのページキャッシュには載っていない。block は 1 つの原本と共有するので、mini 側のキャッシュの状態は全試行で同じ。
  制御したのはクライアント側の cold だけで、sudo の purge は使っていない。
- warm: 書庫ごとに、計測の前にクライアントから SMB 経由で全体を一度読んだ。

### 手順

`2026-10-28-pl7x/run.sh`。まず A 対 A のノイズの幅を測り(各書庫 × warm / cold × 4 回)、次に書庫ごとに warm と cold で ABAB を 4 組ずつ。

## 4. 判定

| 基準(事前に決めたもの) | 結果 |
|---|---|
| warm: B の steady が A の中央値から max(ノイズの幅, 10%) を超えて悪化しない | 合格(3 書庫とも同等以上) |
| warm: B の jump が同じ条件を満たす | **不合格**(big-jpeg 29 → 65、big-tiff 16 → 28)。§1 の理由で累計に改めた |
| warm(改めた基準): open→jump が A + max(ノイズの幅, 10%) 以内 | 合格(68 / 67、35 / 31 は A のノイズの幅 30–37 の内) |
| cold: open→first が A 以下 | 合格(27 / 8,500、22 / 357、30 / 2,682) |
| cold: open→jump が A + max(10%, 100 ms) 以内 | 合格(9,368 / 9,369、406 / 405、5,372 / 5,471) |
| 31v8: big の cold の first が数秒以内 | 合格(20 ms) |

warm で jump が 2.2 倍になるのは、B が 2 回目の要求で走査の遅延を測るという仕組みの結果で、残った不具合ではない。
cooViewer では 1 枚目の直後に先読みが次の要求を出すので、この走査は利用者のジャンプではなく先読みの中で払われる見込みである
(仮説。今回は測っていない)。
